# Project Overview

## 1. วิสัยทัศน์

แอปเดียวที่อยู่กับผู้ใช้ตลอดวงจรของทริป

| ช่วง          | ผู้ใช้อยากทำอะไร                              | ระบบช่วยอะไร                                       |
| ------------- | --------------------------------------------- | -------------------------------------------------- |
| **Planning**  | รู้ว่าจะไปไหน วันไหน งบเท่าไหร่               | Trip, Members, Places, Itinerary รายวัน            |
| **Traveling** | จดเร็ว ไม่อยากเสียเวลากับมือถือ               | Trip Mode: บันทึกค่าใช้จ่าย/โน้ต/เช็กอินใน 2–3 แตะ |
| **Recording** | เก็บความทรงจำไว้ไม่ให้หาย                     | Journal entry + รูป + timestamp + ตำแหน่ง          |
| **Reviewing** | รู้ว่าใช้ไปเท่าไหร่ ใครต้องคืนใคร ไปไหนมาบ้าง | Summary, Timeline, สถิติ                           |

สิ่งที่ทำให้ต่างจาก CRUD demo คือ **ข้อมูลทั้งสามส่วนเชื่อมกัน**
ค่าใช้จ่ายผูกกับสถานที่ได้ บันทึกผูกกับรูปและค่าใช้จ่ายได้ แล้วทั้งหมดไหลมารวมเป็น Timeline เดียว

## 2. ผู้ใช้เป้าหมาย

- กลุ่มเพื่อน/คู่ ที่ไปเที่ยว 2–6 คน ทริปสั้น 2–7 วัน
- มีคนหนึ่งเป็น "คนจด" คนอื่นอาจไม่ได้สมัครบัญชีด้วยซ้ำ
- ใช้มือถือเกือบ 100% ระหว่างทริป ใช้จอใหญ่บ้างตอนวางแผนและย้อนดู

## 4. ข้อสังเกตสำคัญจากการวิเคราะห์

ข้อเหล่านี้ไม่ได้อยู่ใน requirement ตรง ๆ แต่ส่งผลกับการออกแบบมาก

**1. คนร่วมทริป ≠ ผู้ใช้ระบบ**
ทริป 2 คน อีกคนอาจไม่สมัครบัญชีเลย แต่ระบบยังต้องบันทึกได้ว่า "เพื่อนจ่ายค่าข้าว"
ดังนั้น `TripMember` ต้องเป็น entity ของตัวเอง มี `user_id` เป็น optional
และ "คนจ่าย" ของ expense ต้องอ้างถึง member ไม่ใช่ user

**2. "ใครจ่าย" มีค่าก็ต่อเมื่อบอกได้ว่า "ใครต้องคืนใคร"**
แค่เก็บชื่อคนจ่ายยังไม่มีประโยชน์จริง MVP จึงคำนวณยอดเคลียร์แบบหารเท่าให้เลย
(แต่ละคนจ่ายไป − ส่วนที่ควรจ่าย) การหารไม่เท่าเป็นส่วนขยายภายหลัง

**3. Timeline ไม่ใช่ข้อมูล แต่เป็นมุมมอง**
ไม่ต้องมีตาราง timeline เพราะมันคือการเอา journal entry กับ expense มาเรียงตามเวลา
ถ้าเก็บแยกอีกชุดจะต้องคอย sync และวันหนึ่งจะไม่ตรงกัน

**4. Budget ไม่ต้องเป็น entity แยกใน MVP**
งบของทริปคือตัวเลขเดียว เป็น column บน `trips` ได้เลย
งบแยกตามหมวดค่อยเพิ่มตารางใน Phase 6 ถ้าใช้จริงแล้วรู้สึกว่าต้องการ

**5. Itinerary ไม่ต้องมีตารางหัว**
"Day 1, Day 2" คำนวณได้จากวันเริ่ม–วันจบของทริป เก็บแค่รายการ (`itinerary_items`) ที่มีวันที่กำกับก็พอ

**6. Transportation คือรายการหนึ่งในแผน**
"นั่งรถบัส 08:00 มหาสารคาม → โคราช" อยู่ในลำดับเดียวกับ "เที่ยวอนุสาวรีย์ 11:30"
จึงรวมเป็น `itinerary_items` ชนิด `transport` ไม่แยกตาราง

**7. สัญญาณมือถือไม่น่าเชื่อถือ**
ใช้ในงานเทศกาลดนตรีหรือบนรถ สัญญาณจะแย่ ทุกรายการที่สร้างจากมือถือจึงมี `client_id`
ให้ server กันรายการซ้ำได้ตั้งแต่วันแรก ส่วน offline queue เต็มรูปแบบค่อยทำ Phase 7

**8. "Real-time budget" ไม่ต้องใช้ WebSocket**
หมายถึงบันทึกแล้วตัวเลขอัปเดตทันที ซึ่งทำได้ด้วยการคำนวณใหม่ตอนอ่านและ invalidate cache ฝั่ง client

## 5. ขอบเขต

### อยู่ใน MVP

ทุกอย่างใน Phase 1–4 ตาม `docs/FEATURES.md`

### ไม่ทำ (Non-Goals) ในตอนนี้

- จองที่พัก/ตั๋ว หรือเชื่อมระบบจ่ายเงิน
- หลายสกุลเงินในทริปเดียว (1 ทริป = 1 สกุลเงิน)
- หารค่าใช้จ่ายไม่เท่ากันรายรายการ
- แก้ไขพร้อมกันแบบ real-time (WebSocket)
- Social feed, แชร์ทริปสาธารณะ
- Native mobile app
- Notification / LINE integration

ไม่ทำตอนนี้ไม่ได้แปลว่าไม่ทำตลอดไป โครงสร้างที่วางไว้รองรับการเพิ่มทีหลังได้

## 7. คำศัพท์

| คำ             | ความหมาย                                                 |
| -------------- | -------------------------------------------------------- |
| Trip           | ทริปหนึ่งครั้ง มีวันเริ่ม วันจบ งบ และสมาชิก             |
| Member         | คนร่วมทริป อาจผูกกับบัญชีผู้ใช้หรือเป็นแค่ชื่อ (guest)   |
